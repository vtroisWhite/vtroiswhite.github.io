![AI 智能体如何通信的原文配图](/images/posts/how-ai-agents-communicate.png)

AI 智能体通过交换信息、请求协助和传递中间结果，协作完成一项任务。不同角色可以独立工作，也可以按依赖关系相互检查和接续。

## 通信需要哪些部件

[AI 智能体](/posts/ai-agent/)可以调用模型和工具执行工作，[多智能体系统](/posts/multi-agent-systems/)则要把这些角色组织起来。一条通信链通常包括发送者、接收者、消息、协议、通道和共享上下文。消息承载任务、事实或结果，协议约定格式和发送规则，通道可以是网络请求、消息队列或共享存储。

发送者先将结果封装成约定格式，再沿通道发给接收者。接收者读取消息、完成自己的部分，然后回复或继续传给下一位智能体。每一跳都可以记录日志、执行安全检查，或把必要的信息写入共享状态。

```text
   request:   Agent A  ──▶  Channel  ──▶  Agent B
   reply:     Agent A  ◀──  Channel  ◀──  Agent B
```

## 四种通信模式

### 直接通信

调研智能体直接把事实发给写作智能体。写作智能体需要更多资料时直接向调研智能体提问。结构简单，适合参与者较少的流程。角色变多后，各方都要知道怎样联系其他角色，维护连接就更复杂。

```text
Research Agent  ◀───────▶  Writing Agent
```

### 中心化通信

其他智能体统一与[编排者](/posts/ai-orchestration/)交换消息。客服系统可以让中心角色把账单问题发给账单智能体、技术问题发给技术智能体，再接收结果。集中路由便于新增角色、记录和监控。中心角色也可能成为瓶颈或单点故障。

```text
              ┌──────────────┐
   User ◀──▶  │  Main Agent  │
              └──────────────┘
              ▲          ▲
              │          │
              ▼          ▼
          Billing    Technical
           Agent       Agent
```

### 广播通信

发布者把事件发到消息代理，订阅者收到事件后分别处理。以新闻系统为例，发布一篇文章后，摘要、翻译和事实核查智能体可以同时开始工作。发布者无需维护接收者清单，但系统要追踪谁处理了事件，并控制无效订阅带来的流量。

```text
                                  ┌──▶ Summary Agent
   News Agent ──▶ [Broker] ───────┼──▶ Translation Agent
   (Publisher)                    └──▶ Fact-check Agent
```

### 共享记忆通信

多个智能体共同读写一块「黑板」。解决一道数学题时，第一位写下已知值，第二位根据它求出中间结果，第三位接着完成解答。共享状态便于逐步积累结果，需要用写入规则、并发控制和权限约束维持秩序。

```text
   Agent 1 ◀──▶ ┌───────────────────┐ ◀──▶ Agent 2
                │   Shared Memory   │
                │   (Blackboard)    │
   Agent 3 ◀──▶ └───────────────────┘ ◀──▶ Agent 4
```

| 模式 | 信息流 | 适用情形 |
| --- | --- | --- |
| 直接 | 智能体点对点互发 | 角色少，执行顺序固定 |
| 中心化 | 全部经协调者转发 | 需要集中控制和日志 |
| 广播 | 一个发布者通知多个订阅者 | 多个角色并行响应同一事件 |
| 共享记忆 | 所有参与者读写共同状态 | 多个角色逐步完善同一成果 |

系统可以混合使用。例如，主智能体用中心化通信控制全局，在一个阶段让一组执行者用共享存储协作。

## 一条消息长什么样

结构化消息通常包含发送者、接收者、消息类型、内容和背景，例如任务 ID 与历史摘要。下面是一条 JSON 消息。

```text
{
  "sender": "research_agent",
  "receiver": "writing_agent",
  "type": "result",
  "content": "Here are the five key facts about the topic...",
  "context": {
    "task_id": "trip-123",
    "step": "research"
  }
}
```

接收者可以先依据类型判断这是请求、结果还是错误，再按字段读取内容。

## 通信协议与标准

- **[MCP](/posts/what-is-mcp-model-context-protocol/)。** 用统一方式把模型或智能体连接到外部工具及数据。
- **A2A。** 为智能体之间的协作提供协议，可用于不同团队或公司开发的智能体。
- **HTTP 与 REST API。** 在明确的网络接口上交换消息。
- **消息队列。** Kafka、RabbitMQ 等工具允许发送和消费异步进行。

原文指出 MCP 和 A2A 在 Linux Foundation 体系下发挥互补作用。连接后，智能体还需要理解数据代表什么，[开放知识格式 OKF](/posts/what-is-okf-open-knowledge-format/)关注的就是这层含义。同一系统内部可以直接调用 API，需要跨系统协作时再引入通用协议。

## 可靠性与安全

- 约定消息格式，检查每条消息的字段、权限和内容，避免错误数据或恶意指令沿链传播。
- 为丢失和超时设计重试与确认机制，对乱序消息进行处理。
- 限制单个任务的总消息数，避免相互请求形成无穷循环。只传递接收者需要的材料，控制延迟和词元开销。
- 记录发送者、接收者和时间，用[可观测性](/posts/ai-agent-observability/)追踪一次完整执行。
- 给每个角色清楚的职责，用共享状态保留最新任务进度。支付、对外发信等关键操作进入人工审批环节。

## 常见问题

- **MCP 和 A2A 分别解决什么问题？** MCP 连接智能体与工具，A2A 连接不同智能体。
- **大量角色适合点对点吗？** 随着连接增多，可以改用中心化或广播模式。
- **如何防止错误扩散？** 在每次接收时校验消息，对会造成实际影响的操作保留审核。
