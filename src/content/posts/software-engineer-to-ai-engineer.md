软件工程师转向 AI 工程时，已有的 API、系统设计、测试和上线经验都能用上。需要补的是怎样调用大语言模型（LLM）、组织上下文、检索资料、接入工具，以及评估模型的输出。可以用几个小项目把这些环节串起来，再用实测数据展示成果。

## AI 工程师做什么

AI 工程师把已经训练好的模型接入产品。以一个客服助手为例，工程师需要给模型提供退款政策和订单信息，为订单查询配置工具，检验回答是否符合规则，再把整个服务部署到用户可以访问的环境。

- **调用模型。** 接入模型 API，设计提示词，处理超时和调用失败。
- **提供资料。** 用检索增强生成（RAG）找出与问题相关的文档片段，在模型作答前把这些片段交给它。
- **接入工具。** 搭建 AI 智能体，让模型提出工具名和参数，由应用校验并执行调用。
- **检查质量。** 用评估集检验输出，比较改动前后的表现。
- **维护服务。** 部署、监控并控制响应延迟和使用成本。

本文讨论的是应用侧的 AI 工程。模型从零训练通常由研究团队或机器学习工程师负责，转向应用侧时，可以先从已有的工程能力着手。

## 哪些软件工程能力可以复用

| 已有能力 | 在 AI 工程里的用途 |
| --- | --- |
| 调用 API | 为模型服务设置超时、重试和失败时的降级策略 |
| 系统设计 | 规划数据存放位置和请求路径，确定模型变慢时如何处理 |
| 编写测试 | 建立评估集，按规则给输出评分，检查改动有没有引入回归 |
| 排查问题 | 查阅提示词、模型响应和工具调用的链路记录 |
| 数据处理 | 读取文件、清洗文本、分块、入库，再检索相关内容 |
| 缓存 | 复用适合缓存的提示词、嵌入向量或响应 |
| 校验输入 | 验证模型输出的字段、类型和取值范围，再交给下游 |
| 上线运维 | 部署服务，监控响应时间和成本，处理权限与安全问题 |

和编码智能体协作的方式也可以沿用。例如，把任务交给 Claude Code 时，先明确要实现的功能，再审阅它生成的代码，运行测试并检查输出。系统怎么设计、代码是否满足要求，仍要由工程师判断。

## 需要补齐哪些能力

1. **理解模型的行为。** LLM 逐个生成词元（token），同样的输入可能得到不同回答。模型可能很肯定地给出错误信息，单次调用能容纳的文本也受上下文窗口限制。
2. **设计提示词和上下文。** 明确任务、组织资料、挑选示例，并约定输出格式。这些都影响模型拿到什么信息、怎样作答。
3. **理解嵌入与检索。** 嵌入模型把文本映射为向量，系统可以据此按语义相似度检索。这是向量检索式 RAG 的基础。
4. **处理工具调用。** 让模型选择工具，应用校验参数并执行，然后把结果送回模型。还要给循环设定明确的停止条件。
5. **设计评估。** 自由文本往往有多种合格写法。需要先确定评分规则，再用一组相同的样例比较不同提示词或处理流程。
6. **衡量成本和延迟。** 记录词元用量，合理利用缓存，按任务复杂度选择模型。

## 按什么顺序学

### 1. 先跑通一次模型调用

让编码智能体写一个小脚本，通过 API 发送提示词并打印回答，然后审阅代码。试着修改提示词和采样温度，观察结果怎样变化。记录输入和输出的词元数，了解上下文容量以及一次请求的开销。

### 2. 设计提示词并约定输出结构

用系统提示词设定角色和规则，用少量输入和输出样例说明期望结果。让模型返回 `{"category": "billing"}` 这类固定结构的 JSON，方便程序解析并校验。可以把这一步当作给模型和下游服务定义接口契约。

### 3. 用嵌入向量搭建 RAG

把文档切成片段，生成嵌入向量并存进向量数据库。收到问题后，查找最相关的片段，再把问题和片段一起交给模型。编码智能体可以帮忙实现各个环节。要知道检索是否有效，先读一读它实际找回来的片段。

### 4. 接入工具并实现智能体循环

把「查询数据库」「发送邮件」等工具及其参数结构告诉模型。模型提出调用请求，程序执行后将结果反馈给模型，模型再决定下一步。审查编码智能体实现的循环时，重点看它如何结束。限制执行步数，记录工具操作，并在有风险的操作前要求确认。

### 5. 给结果做评估

准备一组测试问题和参考答案，让编码智能体写评分脚本。审阅脚本后先测出基线，再只改一项，例如提示词或分块大小。用同一组测试题重新评分，看看改动有没有改善结果。对自由文本，也可以让另一个模型按明确的规则辅助评分。

### 6. 部署并监控服务

记录提示词、模型响应和工具调用链路，同时监控响应时间和词元用量。日志中的敏感内容需要按规则处理。对可复用的结果加缓存，给调用设预算，并准备主模型失败时可以启用的备用模型。

## 用三个项目验证所学

1. **文档问答应用。** 选一套熟悉的工具文档，搭建 RAG。用 50 道测试题检查正确片段能否进入前 5 条检索结果，以及最终回答是否正确。把测试方法和结果写进 README。
2. **能调用工具的客服智能体。** 让智能体读取客户消息，通过工具查询数据库里的订单，再给出答复或转人工。退款必须先确认。记录正确调用工具的次数、误转人工的次数，以及每项任务平均需要几步。
3. **自动评估工具。** 给前两个项目之一写一个脚本，运行 100 个测试用例，给输出评分并生成报告。只修改一个环节，再跑一遍，把两次结果和改动写入 README。

在每个项目里，先给编码智能体写清任务，然后阅读生成的代码、运行并检查结果。如果 RAG 找回的片段不相关，可以调整分块策略，再跑一遍评估，看问题是否解决。

## 怎样展示转型成果

**简历。** 保留已有的软件工程经历，增加「AI 工程项目」一栏。每个项目用一句话写清范围、工作和评估结果。下面的数字是写法示例，实际简历应填写自己测得的数据。

- 搭建覆盖 2,000 页文档的 RAG 系统，在 50 道题的评估集上取得 87% 的回答准确率。
- 搭建支持 3 个工具、带操作限制的客服智能体，在 100 轮测试对话中，工具选择正确率为 94%。

**介绍转型动机。** 如果你的背景是后端开发，可以说明做 AI 项目时遇到了哪些熟悉的工程问题，例如检索质量、评估、成本和可靠性，再解释自己如何处理它们。

**面试。** 实操题可能要求你用编码智能体给一组文件搭建 RAG，并证明它能工作。说清楚你给智能体下了什么任务，怎样审阅它的代码，以及为什么选择这个分块大小和模型。用评估结果说明答案是否可靠。

**在现公司实践。** 可以找一项适合用 LLM 改善的功能，例如客服工单摘要。实现它，测量效果，再把它上线。实际交付的功能能直观地展示你如何把已有的工程能力用到 AI 产品中。

## 常见问题

### 转向 AI 工程需要学会训练模型吗？

构建基于现有模型的应用，可以从模型调用、检索、工具和评估入手。从零训练模型属于另一类工作，通常由机器学习工程师或研究团队负责。

### 模型评估为什么更难？

很多传统软件测试有明确的通过条件。模型生成的文本可能有几种正确写法，有时还要同时评估准确性、完整性和是否遵循格式。可以为这些维度制定评分规则，用固定样例比较不同版本。

### 有软件工程经验，应该按 AI 新人来介绍自己吗？

可以把既有的系统设计、开发和上线经验作为主线，再用做过的 AI 项目及其评估结果证明新增的能力。

### 有什么容易开始的转型方式？

可以从现有工作里找一个边界清楚的问题，比如给客服工单生成摘要。把需求做成可运行的功能，评估效果并上线，就有了可以具体说明的案例。
