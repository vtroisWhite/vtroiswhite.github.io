上下文工程（Context Engineering）是为大语言模型设计、组织和管理输入的工作。它决定每次调用要提供哪些信息、怎么组织、什么时候放进去，让模型有足够的依据完成当前任务。

## 什么是上下文工程

大语言模型根据[上下文窗口](https://outcomeschool.com/blog/context-window)里的内容预测接下来的词元。我们要给它的不仅是一条指令，还可能包括参考资料、示例、历史消息和工具返回的数据。材料缺失时，模型可能答不出问题，或者给出看似合理的猜测。材料过多时，真正重要的信息又可能淹没在噪声里。

## 把上下文想成一次任务交接

设想一位聪明、做事很快的新同事，但他记不住上次交接过什么。每次分派任务，都要在一份简短说明里告诉他几件事。

- 他在这项任务中的角色。
- 当前要完成的工作。
- 需要阅读的背景资料。
- 可以参照的过往成果。
- 可以使用的工具。
- 需要交付的格式。

同事拿到的是任务简报，模型拿到的是本次调用的上下文。上下文工程要做的是在有限篇幅内，把任务所需的资料交代清楚。

## 为什么上下文工程重要

单次模型调用本身不会记住前一次对话。应用要延续讨论、遵守用户偏好或使用前一次调用的结果，就得从存储里取出有关信息，并在合适的时候送回模型。

有些任务里，拿到准确材料的小模型可以胜过缺少资料的大模型。应用从简单聊天扩展到[检索增强生成（RAG）](/posts/retrieval-augmented-generation-rag/)、智能体和多步工作流后，每一步需要的信息也会变化。选模型和改措辞仍然有用，但检索到了什么、保留了哪些历史、怎样传递工具结果，同样影响最终表现。

## 提示词工程与上下文工程

提示词工程关心指令如何表达。比如，把“总结这篇文章”写成“用三条要点总结这篇文章，面向没有技术背景的读者”，可以明确受众和交付形式。

上下文工程关心这条指令和哪些信息一起交给模型。系统规则、检索资料、示例、工具、记忆和历史消息都在这个范围里，提示词也是其中一部分。

| 比较项 | 提示词工程 | 上下文工程 |
| --- | --- | --- |
| 范围 | 一条指令的措辞与结构 | 模型本次调用可见的全部输入 |
| 常见场景 | 摘要、改写等单次任务 | RAG、智能体、多步工作流 |
| 典型问题 | 任务描述含糊，回答格式不符 | 资料缺失或失效，回答缺少依据或工具用错 |
| 调整方式 | 改写指令、明确受众和输出要求 | 补充检索结果、调整记忆或重新组织信息 |

```text
上下文窗口（上下文工程）
  ├─ 系统提示、示例、检索资料
  ├─ 工具定义、工具结果
  ├─ 记忆、对话历史
  └─ 当前提示（提示词工程）
     “用三条要点向没有技术背景的读者总结文章”
```

## 上下文由哪些部分组成

| 组成 | 作用 |
| --- | --- |
| 系统提示 | 设定角色、规则、行为边界和输出要求 |
| 少样本示例 | 用少量输入和输出的配对，展示模型应遵循的模式 |
| 检索资料 | 从知识库、文档站或数据库取回有关片段。[《什么是 Agentic RAG？它如何工作，何时适用？》](/posts/agentic-rag/) |
| 工具定义 | 告诉模型可用的函数名称、用途和参数结构 |
| 记忆 | 按需带入用户偏好、长期事实和过去对话中的重要信息。[《AI 智能体的记忆如何工作？详解记忆的分层结构》](/posts/ai-agent-memory/) |
| 对话历史 | 保留本次会话的相关轮次，让模型接得上前面的讨论 |
| 工具结果 | 将搜索、计算、查库等工具的执行结果交给下一次模型调用 |
| 当前用户消息 | 提供用户刚提交的问题或指令 |

这些内容共享同一个有限的窗口。一次调用可以没有示例或工具结果，关键是为当前任务选出所需的部分，并控制它们各自的长度。

## 常见做法

应用在每一轮选择所需材料，组装成这一次的模型输入。工具返回新结果后，下一次调用再据此更新输入。

```text
系统提示、示例、检索资料、记忆
工具定义、工具结果、对话历史、用户消息
                    ↓
              组装本次上下文
                    ↓
                 调用模型
                    ↓
          根据新消息或工具结果更新
```

1. **检索增强生成（RAG）。** 只取回与问题相关的知识库片段。先将文档分块，再做向量检索和重排序，有助于挑出最适合交给模型的材料。[分块策略](/posts/chunking-strategies-for-rag/) · [向量数据库](/posts/how-does-a-vector-database-work/) · [重排序](/posts/how-does-a-reranker-work/)
2. **少样本示例。** 放入少量输入与目标输出的配对，让模型从示例中学会要遵循的模式。可以先试 2 到 5 个，再按具体任务调整。
3. **工具调用。** 模型根据工具定义提出调用请求，运行环境执行工具并把结果送回模型。这个过程是[AI 智能体](/posts/ai-agent/)的基础。[Harness Engineering](/posts/harness-engineering-in-ai/)关心智能体运行所需的循环、工具和上下文，[Loop Engineering](/posts/what-is-loop-engineering/)则聚焦于循环本身，比如允许执行几轮、哪些状态带到下一轮、何时停止。
4. **注入相关记忆。** 为每轮检索与当前任务有关的长期事实和偏好，按需放进上下文。
5. **管理对话历史。** 对话过长时，可使用[摘要](https://outcomeschool.com/blog/how-does-context-compaction-work)、滑动窗口或选择性保留，把历史控制在可用额度内。
6. **约定输出格式。** 可以在上下文中要求 JSON、Markdown 表格或固定表单。下游程序需要稳定解析时，优先使用模型支持的结构化输出和 JSON Schema 约束。
7. **压缩上下文。** 对过长的材料做摘要、提取关键事实或改写成结构化数据，尽量保留原意并减少词元。
8. **按步骤重新组装。** [智能体循环](/posts/ai-agent-loop/)中，每一步都可能有新工具结果、已完成的子任务或更新后的计划。下一步只带入当前子任务需要的状态和证据，避免历史输入一直增长。

## 容易踩的坑

1. **塞入过多信息。** 大量无关材料会抬高成本、增加延迟，也可能让模型更难找到答案。随着上下文增长而出现的质量下降，常被称为上下文退化（context rot）。只保留本轮任务需要的内容。
2. **缺少必要信息。** 如果要模型按公司的退款规则回答，就应让它看到有关规则。散落在内部 Wiki、代码注释或同事经验里的知识，需要先整理成能被检索和读取的资料。[开放知识格式（OKF）](/posts/what-is-okf-open-knowledge-format/)提供了一种用 Markdown 组织这类知识的方式。
3. **关键内容放得太深。** 长上下文中，一些模型对中间位置的信息利用较弱。这种现象叫[中间遗失（lost in the middle）](/posts/lost-in-the-middle-problem-in-llms/)。通常把稳定规则放在前面，把当前任务放在末尾，再按实际模型和任务评估效果。
4. **保留了过期信息。** 已经失效的工具结果、旧文档和无关历史会干扰判断。进入新步骤时，及时移除不再适用的材料。
5. **材料缺少结构。** 一整块文本会让指令、证据和历史消息混在一起。用标题、分隔符和统一标签标出它们各自的边界。
6. **指令或材料相互冲突。** 用户要求可能与系统规则冲突，两份参考资料也可能给出不同结论。明确规则的优先级和处理资料冲突的办法，让模型知道本轮该怎么做。

## 实践建议

1. **分配词元预算。** 提前给系统提示、检索资料、对话历史和当前任务分配额度，避免某一部分占满整个窗口。
2. **围绕本轮任务选材料。** [Agent Skills](/posts/what-are-agent-skills/)也用到了这个思路。先提供简短的技能描述，需要执行对应任务时再读取详细步骤。
3. **把稳定内容放在前面。** 可以依次放系统提示、示例、检索资料、记忆和历史，最后放本轮消息。稳定的共同前缀也便于使用[提示词缓存](/posts/how-does-prompt-caching-work/)。
4. **明确各段边界。** 标出系统指令、示例、资料、历史和当前任务。下面是一种简化结构。

   ```text
   ### 系统指令
   你是一名助手……

   ### 示例
   示例 1……
   示例 2……

   ### 检索资料
   [资料 1]……
   [资料 2]……

   ### 对话历史
   用户……
   助手……

   ### 当前任务
   用户……
   ```

5. **测试上下文。** 任务失败时，检查模型实际收到了哪些信息。为便于复现，可记录失败时的输入，按应用的隐私要求对敏感数据脱敏并限制访问。
6. **管理上下文的变更。** 对模板、检索规则和组装逻辑做版本管理，比较差异，通过 A/B 测试和真实任务评估改动。
7. **谨慎压缩。** 摘要会丢失细节。后续步骤还要核对原文、参数或决策依据时，应保留对应的原始内容或引用。
8. **为长输入留余量。** 用长对话、大文档和连续[工具调用](/posts/how-does-function-calling-work-in-llms/)测试系统，确认接近上限时仍能保留任务所需的信息。

## 小结

为每次模型调用组装上下文时，可以先写清楚当前任务和交付要求，再补充任务所需的资料、示例、工具和历史。输入接近上限时，优先删掉过期或无关的信息。排查回答失败时，从当时送入模型的内容开始检查。

## 常见问题

### 上下文窗口越大，回答越好吗？

更大的窗口允许传入更多信息。回答是否更好，还要看额外内容是否与任务有关，以及模型能否有效利用这些内容。

### 上下文更好的小模型能超过大模型吗？

在某些任务上可以。比如，拿到正确退款规则的小模型可能比没有这份资料的大模型答得更准确。

### 大语言模型会记住上一次调用吗？

跨调用的记忆通常由应用或服务负责。需要沿用之前的信息时，系统会从会话或存储中取回相应内容，再提供给模型。

### 长上下文里的关键指令放在哪里？

可以把稳定规则放在开头，把用户当前的任务放在末尾，并用实际任务验证布局是否有效。

### 在提示词里要求 JSON，程序就能稳定解析吗？

提示词可以引导模型输出 JSON。下游程序依赖固定结构时，使用支持结构化输出的 API 和 JSON Schema 约束，并在接收端校验。
